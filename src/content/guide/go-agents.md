## 에이전트란

Go에서 에이전트는 실행 단위입니다. "누구인가, 어디에서 일할 수 있는가, 어떻게 행동해야 하는가"를 한 묶음으로 정해 둔 것입니다. 이렇게 묶어 두면 같은 작업을 여러 번 돌려도 결과를 예측하기 쉽습니다.

에이전트는 **Settings > Agents**에서 만들고 관리합니다. 예전 용어는 Bots였고, 지금 제품 용어는 Agents입니다.

예를 들어(필자가 든 예입니다) 홍보팀 보도자료 폴더만 읽고 쓰는 "보도자료 정리 에이전트"와, 코드 저장소 하나만 다루는 "코드 검토 에이전트"를 따로 만들 수 있습니다. 서로의 폴더를 건드리지 못하게 범위를 나누는 것이 핵심입니다.

## 에이전트를 이루는 다섯 가지

| 항목 | 정하는 것 |
|---|---|
| Workspace | 어느 작업 공간에서 일하는가 |
| Routing mode | 로컬에서만 쓰는가, 원격 채널과 연결하는가 |
| Runtime mode | 내 컴퓨터에서 바로 실행하는가, 컨테이너 안에서 실행하는가 |
| Permission profile | 무엇을 할 수 있는가 |
| Working style | 어떤 태도로 계획하고 실행하는가 |

## 첫 에이전트를 만드는 순서

문서가 "처음에 실패하지 않는 패턴"으로 제시한 순서입니다.

1. 작업 공간 범위를 고릅니다(`Managed` 또는 `Project folder`).
2. 실행 방식을 고릅니다(`Host` 또는 `Container`).
3. 경로를 정합니다(`Local only` 또는 채널 프리셋).
4. 권한과 보안 제약을 적용합니다.
5. 작업 방식을 정하거나 확인합니다.
6. 안전한 검증 작업을 한 번 실행합니다.

초기 에이전트는 단순하게 유지합니다. 그래야 실패했을 때 원인을 찾기 쉽습니다.

## 작업 공간 선택

| 선택지 | 뜻 | 쓰는 경우 |
|---|---|---|
| `Managed` | Go가 관리하는 격리된 작업 공간 | 격리가 필요하거나 실험할 때 |
| `Project folder` | 이미 있는 저장소나 문서 폴더에서 실행 | 기존 프로젝트를 알고 작업해야 할 때 |

`Project folder`를 고르면 작업에 필요한 경로로만 접근을 좁게 잡습니다.

작업 공간 루트에 `SOUL.md`, `IDENTITY.md`, `USER.md`가 있고 그 내용이 에이전트 행동에 반영되어야 할 때만 [작업 공간 프로필 파일](/guide/go-workspace-profile-files/)을 켭니다.

## 경로 선택

| 선택지 | 뜻 |
|---|---|
| `Local only` | 원격 채널에 의존하지 않습니다 |
| `Channel preset` | 재사용할 수 있는 원격 목적지와 발신자 정책을 붙입니다 |

`Local only`로 시작하고, 에이전트 동작이 안정된 뒤 채널 경로를 더합니다. 첫 검증에서 전송 경로와 발신자 정책까지 한꺼번에 따지지 않기 위해서입니다. 채널 프리셋은 [채널](/guide/go-channels/)에서 설명합니다.

## 실행 방식 선택

| 선택지 | 뜻 | 쓰는 경우 |
|---|---|---|
| `Host` | 내 컴퓨터에서 직접 실행 | 로컬에서 빠르게 반복할 때 |
| `Container` | Docker 또는 Podman 안에서 실행. macOS는 OrbStack 지원 | 더 강한 격리가 필요할 때 |

Container를 고르면 다음을 조절할 수 있습니다.

- 네트워크 켜기/끄기
- 셸·터미널 접근
- 웹 접근 동작(네트워크 설정에 따라 달라집니다)
- 필요한 도구와 패키지를 넣은 사용자 정의 컨테이너 환경(선택)

문서의 기준은 위험도입니다. 민감한 작업을 다루는 에이전트라면 반복 속도가 느려지더라도 격리가 강한 쪽을 고릅니다.

컨테이너에서 도우미(하위) 에이전트를 쓰는 작업이라면 환경 구성을 명시적으로 유지하라고 합니다. 위임된 작업이 모두 같은 도구를 갖고 실행되도록 하기 위해서입니다.

## Computer Use

Go는 macOS와 Windows에서 Computer Use를 지원합니다. 호환되는 에이전트에서 켜면 에이전트가 데스크톱 화면을 더 직접 다룰 수 있습니다. Linux 지원 여부는 공식 문서에 설명이 없습니다.

문서의 지침은 분명합니다. 화면 조작이 정말 필요한 작업에만 쓰고, 파일·API·셸 도구로 끝낼 수 있는 작업에서는 꺼 둡니다.

- 책임자가 분명한 에이전트에서만 켭니다.
- 엄격한 발신자 정책, 권한 정책과 함께 씁니다.
- 넓게 쓰기 전에 위험이 낮은 상황에서 먼저 검증합니다.
- 셸, 파일, API, MCP 접근만 필요한 에이전트에서는 끕니다.

설치 방법은 [도구 설정](/guide/go-tools/)의 Computer Use 항목에 있습니다.

## 에이전트에 할 수 있는 동작

문서가 든 수명 주기 동작은 일곱 가지입니다.

| 동작 | 설명 |
|---|---|
| Create | 새로 만듭니다 |
| Edit | 설정을 고칩니다 |
| Clone | 복제합니다 |
| Open chat | 에이전트와의 대화를 엽니다 |
| Open activity | 활동 기록을 엽니다 |
| Stop | 실행을 멈춥니다 |
| Delete | 삭제합니다 |

운영 중인 중요한 에이전트는 설정을 그 자리에서 고치지 말고, 복제한 뒤 검증하는 방식을 기본으로 삼으라고 합니다.

## 로컬 대화를 에이전트로 넘기기 (Local chat handoff)

일반 대화를 하다 보면 쓸 만한 맥락이 쌓였는데, 이제 실행 주체가 필요해지는 때가 있습니다. 이럴 때 로컬 대화를 에이전트에 넘길 수 있습니다.

넘기기가 하는 일은 다음과 같습니다.

- 기존 대화 세션을 실행 중인 에이전트에 붙입니다.
- 지금까지의 대화 기록과 세션 상태를 유지합니다.
- 가능한 경우 제공업체·모델 맥락을 이어 갑니다.
- 작업 공간 경로와 폴더 접근을 유지하고, 필요하면 원래 대화와 대상 에이전트의 폴더 접근을 합칩니다.
- 맞는 에이전트가 없으면 대화에서 새 에이전트를 만듭니다.

대화가 반복할 만하거나 권한이 필요한 작업으로 자랐을 때 씁니다. 사소한 대화에는 쓰지 않습니다. 에이전트를 만들면 관리할 상태가 하나 더 생기기 때문입니다.

넘기기 버튼의 정확한 위치는 공식 문서에 설명이 없습니다.

## Mission Control과의 관계

여러 에이전트가 움직이는 복잡한 실행은 [Mission Control](/guide/go-mission-control/)에서 추적하고 검토합니다.

- 실행 주체는 **Agents**에서 만들고 관리합니다.
- 새 맥락으로 시작하는 도우미와 승인은 Mission Control에서 조율합니다.
- 자주 쓰는 도우미 프리셋은 **Settings > Task Force**에서 설정합니다.

## 운영 요령

- 운영 프로필을 건드리지 않고 동작을 시험하려면 복제해서 씁니다.
- 가능하면 에이전트 하나에 목적 하나만 둡니다.
- 설정을 크게 바꾼 뒤에는 활동 기록을 검토합니다.
- 작업 공간이나 실행 방식이 바뀌면 권한을 다시 검증합니다.

에이전트 수가 늘면 이름 규칙과 담당자 지정이 중요해집니다. 에이전트마다 목적과 담당자를 분명히 해 둡니다.

## 알아 둘 점

- 만들 수 있는 에이전트 수의 한도는 공식 문서에 설명이 없습니다.
- Permission profile의 구체적인 항목과 기본값은 이 문서 페이지에 나열되어 있지 않습니다. 관련 통제는 [보안 설정](/guide/go-security/)에서 다룹니다.
