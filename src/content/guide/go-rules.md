## Rules란

**Rules**는 작업 흐름에서 반복되는 순간에 Go의 행동을 정해 두는 기능입니다. 규칙 하나는 세 가지로 이루어집니다.

- 이벤트: 언제
- 조건(선택): 무엇과 일치할 때
- 동작: 무엇을 할지

**Settings > Rules**에서 만들고 관리합니다.

예를 들어(문서가 든 예입니다) "`git push` 명령은 사용자가 직접 올리기로 결정할 때까지 막는다"는 규칙을 만들 수 있습니다. 이벤트는 동작 실행 전, 조건은 명령 문구, 동작은 차단입니다.

## 언제 쓰는가

Go가 다음을 반복해서 해 주기를 바랄 때 씁니다.

- 답하기 전에 늘 지켜야 할 지침 따르기
- 조건에 맞는 위험한 명령을 실행 전에 멈추기
- 도구 결과 뒤에 맥락 덧붙이기
- 파일 수정 같은 동작 뒤에 후속 조치 하기
- 해당 작업 뒤에 범위가 좁은 점검 실행하기

Rules는 운영 통제 수단입니다. [Working Styles](/guide/go-working-styles/), 권한, 승인, [보안 설정](/guide/go-security/)을 보완합니다.

## 규칙의 구성 항목

| 항목 | 설명 |
|---|---|
| Name | 이름 |
| Description | 설명 |
| Enabled/disabled | 켜짐·꺼짐 상태 |
| Event | 언제 작동하는가 |
| Matcher | 조건(선택) |
| Action | 무엇을 하는가 |
| Source/scope | 출처와 적용 범위 |

Source/scope에서 고를 수 있는 값이 무엇인지는 공식 문서에 설명이 없습니다. [Extensions](/guide/go-extensions/) 문서는 확장 기능이 Rules를 제공할 수 있다고 적습니다.

## 지원하는 이벤트

현재 실제로 연결되어 있는 이벤트는 네 가지입니다.

| 이벤트 | 시점 |
|---|---|
| **When a chat starts** | 대화가 시작될 때 |
| **Before Go replies** | Go가 답하기 전 |
| **Before an action runs** | 동작이 실행되기 전 |
| **After an action finishes** | 동작이 끝난 뒤 |

문서는 한 가지를 미리 알려 둡니다. 앞으로의 확장을 위해 내부 모델에 다른 이벤트 이름이 보일 수 있지만, 일상적으로 믿고 쓸 수 있는 것은 위 네 가지입니다.

## 조건으로 쓸 수 있는 것

- 프롬프트나 입력 문구
- 동작·도구의 분류
- 특정 동작·도구의 이름
- 명령 문구
- 동작이 끝난 뒤의 도구 결과 문구

도구 분류에는 흔한 묶음이 포함됩니다. 문서가 든 것은 명령, 파일 변경, 파일 읽기·검색, 웹 동작, 도우미 에이전트, 작업 목록 갱신, 그리고 특정 사용자 정의 동작 이름입니다.

문구 조건이 단순 포함 검사인지 정규식을 쓸 수 있는지는 공식 문서에 설명이 없습니다.

## 다섯 가지 동작

쓸 수 있는 동작은 이벤트에 따라 달라집니다.

| 동작 | 하는 일 |
|---|---|
| **Add guidance** | Go가 답하기 전에 지켜야 할 지침을 더합니다 |
| **Stop an action** | 조건에 맞는 동작을 실행 전에 막습니다 |
| **Add a note after an action** | 도구 결과에 맥락을 덧붙입니다 |
| **Ask Go to follow up** | 해당 작업 뒤에 할 후속 지시를 걸어 둡니다 |
| **Run a command** | 조건에 맞는 도구 사용 전이나 후에 정해 둔 명령을 실행합니다 |

`Run a command`는 조심해서 씁니다. 명령은 범위가 좁고, 실행할 때마다 결과가 같고, 예상한 작업 공간 안으로 한정되어야 한다고 문서는 적습니다. 자동으로 실행되는 명령은 사람의 확인 없이 돌기 때문입니다.

## 규칙이 작동하면 Go는 무엇을 보는가

- 규칙이 동작을 막으면, Go는 어느 규칙이 막았는지 설명하는 도구 오류를 받습니다.
- 규칙이 후속 지시나 명령 출력을 더하면, Go는 그것을 그 턴의 맥락 일부로 봅니다.

차단되었을 때 Go가 이유를 알 수 있으므로, 같은 동작을 무작정 다시 시도하지 않고 다른 방법을 찾거나 사용자에게 알릴 수 있습니다. 뒤 문장은 문서의 동작 설명에서 필자가 끌어낸 해석입니다.

## 처음 만들어 볼 만한 규칙

문서가 든 출발용 패턴입니다.

| 목적 | 이벤트 | 동작 |
|---|---|---|
| 프롬프트에 배포 작업이 언급되면 배포 점검표를 상기시키기 | Before Go replies | Add guidance |
| 사용자가 직접 결정할 때까지 `git push` 막기 | Before an action runs | Stop an action |
| 파일 수정 뒤 후속 검토 요청하기 | After an action finishes | Ask Go to follow up |
| 조건에 맞는 파일 변경 뒤 작은 테스트나 검증기 실행하기 | After an action finishes | Run a command |

목적 열은 문서의 예이고, 이벤트와 동작 열은 문서의 이벤트·동작 설명에 맞춰 필자가 짝지은 것입니다.

처음부터 모든 것을 잡는 넓은 규칙은 피합니다. 원인을 찾기 어렵고, Go의 행동이 일관되지 않게 느껴질 수 있습니다.

## 도입 순서

1. 반복되는 패턴 하나에 규칙 하나를 만듭니다.
2. 중요하지 않은 대화에서 시험합니다.
3. 의도한 때에만 작동하는지 확인합니다.
4. 왜 만들었는지 적어 둡니다.
5. 첫 규칙이 예측대로 움직인 뒤에만 규칙을 더합니다.

규칙 이름은 구체적으로 짓습니다. 나중에 다른 사람이 이름과 설명만 보고 의도한 동작을 이해할 수 있어야 합니다.

## Rules와 보안의 관계

문서는 이 점을 두 페이지에서 반복합니다. Rules는 강제 보안 통제를 대신하지 못합니다.

| 정하려는 것 | 쓰는 곳 |
|---|---|
| 발신자, 폴더, 네트워크, 승인 정책 | [보안 설정](/guide/go-security/) |
| 실행 방식과 권한 범위 | [에이전트](/guide/go-agents/) |
| 웹사이트 접근 정책 | [Airlock](/guide/go-airlock/) |
| 응답 태도 | [Working Styles](/guide/go-working-styles/) |

예를 들어 민감한 폴더를 보호하려면 "그 폴더를 건드리지 마라"는 규칙이 아니라 Allowed Folders와 Blocked Patterns로 접근 자체를 막아야 합니다. Rules는 그 위에 얹는 추가 안전망입니다.

## 알아 둘 점

- 규칙을 몇 개까지 만들 수 있는지, 여러 규칙이 동시에 일치할 때의 적용 순서는 공식 문서에 설명이 없습니다.
- 에이전트별로 다른 규칙을 적용하는 방법도 이 문서 페이지에 적혀 있지 않습니다.
- General Settings 문서에 따르면 설정 검색에서 만들어 둔 규칙을 바로 찾을 수 있습니다.
